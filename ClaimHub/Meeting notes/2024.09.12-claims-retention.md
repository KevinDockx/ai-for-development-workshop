# Claims retention / correction discussion

**12 September 2024**  
**Present:** Nadia Peeters, Sofie Vermeulen, Anouk Willems, Bram Jacobs

We started with a question about removing duplicate test claims after UAT. That quickly became a broader discussion about deleting real claims.

Nadia’s answer was straightforward: a claim file is part of the decision record. If somebody registered it in error, it can be withdrawn with a reason. If information is wrong, both the correction and the original value need to remain traceable. Closing a file does not make it disposable.

Sofie confirmed that the database backup policy is not a substitute for application history. Restoring a backup to explain one deletion is not workable.

For UAT, generated records may be cleared by resetting the complete environment. The application itself should not expose a permanent-delete operation for claims. We will use soft deletion where records must disappear from normal lists and retain the audit trail.

Bram mentioned that the Admin page still has a Delete handler copied from the prototype. It needs changing, but not in the release currently being stabilized.

## Actions

- Nadia: define the withdrawal reasons needed by handlers.
- Bram: replace the Admin delete flow with withdrawal or soft delete.
- Anouk: add a check that deleted/withdrawn claims remain in audit history.
- Sofie: document whole-environment cleanup for synthetic UAT data.
